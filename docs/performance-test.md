# 终端性能测试

测试基线：`cb838de`，Apple M4 / 32 GB、macOS 27.0.1，`cargo build --release --locked -p lure-desktop`，默认 960 × 640 窗口。使用独立临时 `HOME` 和 `LURE_PI_PATH` 指向本地测试子进程，经过实际窗口和 PTY，不使用真实 Pi、模型或网络。采样用 `ps` 的进程累计 CPU 时间和 RSS；CPU 100% 代表一个逻辑核，RSS 不是堆分配量。

## 输出和常驻

| 负载 | 观测结果 |
| --- | --- |
| 80 字符 + CRLF，连续输出 32 MiB / 128 MiB | 两轮分别约 0.15–0.17 秒 / 0.59–0.70 秒收到末尾 VT 查询应答。写完后查询应答不到 1 ms；应答只验证数据已被终端解析，不表示最后一帧已经显示。 |
| 32 MiB 连续 CRLF | 约 0.25 秒收到末尾应答，其中约 25 ms 在写完之后。主线程采样命中终端解析和网格滚动。 |
| 每秒 20 次重绘，每次更新 20 × 80 个交替颜色的字符，持续 60 秒 | 采样轮 Lure 进程平均 CPU 约 21%，RSS 约 129–134 MiB。主线程栈命中文字绘制、字形边界索引插入和可见网格转为文本段。 |
| 大量输出后保留同一窗口和子进程，静默 5 分钟 | 平均 CPU 约 0.35%，RSS 约 112–118 MiB，未见持续上升。结束时 VT 探针仍有应答。该窗口在测试期间不保证始终位于前台。 |

文本回滚历史配置为 10,000 行（[网格构造](../crates/lure-desktop/src/terminal.rs#L401)），绘制读取可见网格，不是每帧遍历全部历史。5 分钟的单会话纯文本测试不能排除数小时、多标签或图像输出下的慢增长。

## 空闲后首次滚动与输入

先写入 12,500 行彩色文本填满回滚历史，比较同一窗口在空闲前和连续静默 120 秒后的表现。使用 macOS 原生合成滚轮和方向键事件；用窗口截图检查终端像素变化，同时让子进程记录收到按键的时间。

| 指标 | 空闲前 | 空闲 120 秒后 |
| --- | ---: | ---: |
| 首次向上滚动后，第一张检查到视口变化的截图 | 142 ms | 146 ms |
| 滚动后按方向键，PTY 子进程收到按键 | 39 ms | 33 ms |
| 按键后，第一张检查到终端区域变化的截图 | 158 ms | 164 ms |

每个条件各测一次。截图数字包含截图采集开销，是粗略上界，不是渲染耗时；按键后画面变化也可能包含回到视口底部，不能当作独立的回显延迟。此轮没有复现显著变慢，但未覆盖数小时后、系统休眠唤醒后、真实 Pi 编辑框、中文输入法或连续触控板滚动。

## 已定位的热点与待验证的风险

- **绘制热点已采到。** 每次重绘提取整个可见网格、重新生成文本段并绘制，即使只有光标或输入行变化。交替颜色会拆出大量文本段；多列 ASCII 文本段还有一次用于测宽的塑形请求。评估脏行复用时，应与现状对比，并在滚动、单行回显及彩色重绘上同时测量延迟与正确性。见 [可见网格转换](../crates/lure-desktop/src/terminal.rs#L733) 和 [窗口绘制](../crates/lure-desktop/src/main.rs#L1434)。
- **输出积压是架构风险，还不是长开后卡顿的定论。** [PTY 事件队列](../crates/lure-pty/src/lib.rs#L215)和 [桌面消息队列](../crates/lure-desktop/src/main.rs#L142)均无容量上限，解析和输入处理又在同一 UI 线程。生产快于消费时，没有应用级的排队内存上限。验证该风险时，应记录待处理字节数、队列等待时间以及帧间隔；只有复现积压后，才应考虑引入背压与分批让出 UI 线程，并确保不丢终端字节。
- **区分 Lure 和 Pi 的耗时。** 普通回滚由 Lure 本地完成；备用屏幕或鼠标报告模式会把滚轮输入转发给子进程。键盘卡顿需要把事件分成 UI 接收、PTY 写入、子进程回显、首帧显示四段；中文输入还要单独覆盖输入法组合过程。见 [键盘写入](../crates/lure-desktop/src/main.rs#L749)和 [滚轮分流](../crates/lure-desktop/src/main.rs#L826)。

## 可见行复用：优化前后短测

优化后只为变化的可见行重建文本段和 GPUI 字形布局；普通回滚或历史前移时，也尝试复用仍在视口内的行。复用前比较实际文本和样式，缓存不随历史增长。最终绘制仍覆盖可见区域，图片、选区和光标绘制顺序不变。

同一台 Mac、相同 Release 配置，先填满回滚历史，再以约 60 Hz 持续改写一行 80 个逐字变色的字符，其他行维持彩色内容。按「旧 → 新 → 新 → 旧」运行，每版共测 32 次滚轮和 32 次方向键。方向键在滚轮回到底部后发送，测试子进程收到后切换首行背景色；通过 ScreenCaptureKit 检查滚动区域或首行的像素变化。以下时间包含截图采样开销，数值越低越好。

| 指标 | 优化前 | 优化后 |
| --- | ---: | ---: |
| 滚轮到画面变化（中位数 / P95） | 53.8 / 76.2 ms | 53.9 / 62.8 ms |
| 方向键到回显（中位数 / P95） | 56.2 / 92.6 ms | 55.5 / 65.1 ms |
| 方向键到达 PTY 子进程（中位数 / P95） | 7.2 / 30.9 ms | 6.0 / 28.6 ms |
| 交互采样期 Lure 平均 CPU（100% 为一核） | 23.9% | 22.0% |

中位响应基本不变，这组短测的慢样本减少了。样本较少，只覆盖单会话、局部彩色更新和合成方向键；不代表整屏持续变化、中文输入法或两小时后真实 Pi 编辑框的表现。

## 复测方法

1. 用 `cargo build --release --locked -p lure-desktop` 构建，并设置临时 `HOME`，在其中创建 `.pi/projects.yaml` 指向临时项目。把 `LURE_PI_PATH` 指向可执行测试脚本，启动 Lure 并打开该项目。
2. 测试子进程把 PTY 设为原始模式，写入表中指定的负载。用最后一个 Kitty 键盘协议查询 `ESC [ ? u` 和 Lure 的 `ESC [ ? 0 u` 应答划定解析完成时间。不要把应答延迟当作显示延迟。
3. 用 `ps -p <PID> -o %cpu=,time=,rss=` 在压力阶段采样，用 `sample <PID> 6 2 -file profile.txt` 捕获彩色重绘时的线程栈。要保留源码定位，可额外用 `cargo rustc --release --locked -p lure-desktop --bin lure-desktop -- -C strip=none -C debuginfo=line-tables-only` 生成采样构建。
4. 长时卡顿复测应使用真实 Pi、与现场相同的标签数和输出类型，记录窗口是否在前台、是否切换过窗口或标签、是否经过锁屏或睡眠，以及卡顿只发生在第一次操作还是持续发生。

## 拖选事件链路诊断

使用 `LURE_TRACE_SELECTION=1 cargo run -p lure-desktop 2> /tmp/lure-selection-trace.log` 启动，拖动鼠标后保持左键按下约两秒，再松开。日志记录相对时间、按下、移动及按钮状态、选区终点更新、渲染、绘制、释放、窗口失焦和 PTY 输出清除选区；不记录终端文本或剪贴板内容。默认不启用。

- 松开前没有「移动」：检查平台事件传递。
- 有「移动」而没有「更新选区」：检查左键状态、活动拖选状态、Pi 鼠标报告模式，以及失焦或 PTY 输出导致的取消。
- 有「更新选区」而没有「渲染／绘制」：检查通知与帧调度。
- 松开前已「绘制」但屏幕未更新：继续检查平台呈现，不能只凭绘制日志判定修复成功。
